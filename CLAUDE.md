# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build / Run / Test

Spring Boot 3.3.4 + Kotlin 1.9.25 on JDK 21, Gradle (Kotlin DSL) multi-module project. No lint task is configured.

```bash
# Run the app (must specify a profile — there is no default datasource in application.yml)
./gradlew bootRun --args='--spring.profiles.active=local'

# Assemble the bootable jar (api.jar; asciidoctor → REST Docs → static/docs)
./gradlew build

# All tests
./gradlew test

# One test class or method (Kotest on JUnit Platform)
./gradlew test --tests 'com.beside.groubing.groubingserver.domain.bingo.api.BingoBoardCreateApiTest'
./gradlew test --tests '*BingoBoardCreateApiTest*'

# Regenerate REST Docs (tests → snippets → asciidoctor → copyDocument to static/docs)
./gradlew asciidoctor
./gradlew copyDocument
```

The `build` task chains `copyDocument` ← `asciidoctor` ← `test`. Broken/skipped tests block `./gradlew build`. Test filter `includeTestsMatching("com.beside.groubing.*")` silently skips tests outside that package.

QueryDSL Q-classes are generated by `kapt` from **entity classes in `gb-db-core`**. If IntelliJ cannot resolve `QXxxEntity` types, run `./gradlew :infrastructure:storage:gb-db-core:kaptKotlin` (or any build task).

## Spring Profiles

- `local` — H2 in-memory (`jdbc:h2:mem:groubing`), `ddl-auto=create`, runs `data-local.sql` on startup (note `defer-datasource-initialization: true`).
- `prod` — MySQL, `ddl-auto=none`. Credentials are checked in; do not change without coordinating.

### Config is distributed per-module, merged by an `EnvironmentPostProcessor` (meet-again pattern)

There is **no central `application.yml`**. Each module owns the config it consumes, under `src/main/resources/config/`:
- `gb-boot-web/src/main/resources/application.yml` (root) — app-wide common (multipart cap).
- `gb-db-core/.../config/application.yml` — JPA common (`open-in-view: false`, `default_batch_fetch_size: 100`, ...); `config/application-local.yml` (H2 datasource) + `config/application-prod.yml` (MySQL datasource), each gated by `spring.config.activate.on-profile`.
- `gb-id-obfuscator/.../config/application.yml` — `id-obfuscator.salt` / `min-length`.

`GbEnvironmentPostProcessor` (in `gb-config-yaml-importer`, registered via `META-INF/spring.factories`) scans **`classpath*:`** (all jars) for `application.{yml,yaml}` (root common), `config/application.{yml,yaml}` (module common), then `config/application-*.{yml,yaml}` (profile-matched, overrides), and merges them into one high-priority `MapPropertySource`. The `classpath*:` glob is what lets multiple modules each ship a `config/application.yml` without colliding (standard `classpath:` loading would pick only one). **A module that needs to read its own config at runtime must be on boot-web's runtime classpath** (e.g. `runtimeOnly` for the importer; `implementation` for db-core/id-obfuscator).

The EPP **no-ops when no profile is active**, so starting without a profile still fails (by design — `local`/`prod` must always be specified). Persistence-test config (`gb-db-core/src/testFixtures/.../application-test.yml`) stays at resource root and is loaded by standard Spring + the EPP common pass.

## Module Layout

```
boot/
  gb-boot-web/              # @SpringBootApplication + @RestController + response DTOs + REST Docs source
config/
  gb-config-yaml-importer/  # GbEnvironmentPostProcessor + spring.factories (merges per-module config/*.yml; holds no yaml itself)
  gb-config-logging/        # logback-spring.xml
domain/
  gb-domain-core/           # pure domain (no JPA) + ports + VOs + events + exceptions + @Service application layer + input commands
infrastructure/
  storage/
    gb-db-core/             # JPA entities + QueryDSL DAOs + repository adapters + BaseEntity/BaseAggregateRoot
  support/
    gb-jwt-core/            # JwtProvider + JwtTokenManager adapter
    gb-crypto-core/         # PasswordEncryptor port + BCrypt adapter
    gb-fcm-sender/          # FCM push (firebase-admin exposed via java-library api)
    gb-id-obfuscator/       # HashidsIdObfuscator (IdObfuscator port impl) + owns config/application.yml (id-obfuscator.salt)
```

Dependency direction (enforced by Gradle project deps):
`boot-web` → `gb-domain-core` + `gb-db-core` + support modules → `gb-domain-core`.
`gb-domain-core` depends on nothing except spring-boot-starter + spring-tx (for `@Component`, `@Transactional`). No JPA, no database.

## Package Layout Inside Each Module

Root package `com.beside.groubing.groubingserver` is **parallel-shared** across modules — leaves differ. Example for a domain like `bingo`:

```
gb-domain-core/com/beside/groubing/groubingserver/domain/bingo/
├── application/            # @Service per use case (BingoBoardCreateService, BingoBoardDeleteService, ...)
├── domain/                 # Pure domain objects (BingoBoard, BingoItem, BingoMember, BingoBoardDetail, ...)
│   ├── map/                # BingoMap, BingoLine, Direction — pure algorithms
│   └── port/               # BingoBoardCommandRepository, BingoBoardQueryRepository
├── event/                  # BingoCompleteEvent, BingoLineCompleteEvent, ... (data classes)
├── exception/              # BingoInputException, BingoIllegalStateException
└── payload/command/        # BingoBoardCreateCommand, etc. (input DTOs for services)

gb-db-core/com/beside/groubing/groubingserver/domain/bingo/
├── entity/                 # BingoBoardEntity + BingoItemEntity + BingoMemberEntity + BingoCompleteMemberEntity + *Embeddable VOs
├── repository/             # BingoBoardJpaRepository (JpaRepository) + BingoBoardRepositoryAdapter (implements ports)
└── dao/                    # QueryDSL read DAOs (BingoBoardListFindDao) — internal to the adapter

gb-boot-web/com/beside/groubing/groubingserver/domain/bingo/
├── api/                    # @RestController per use case (BingoBoardCreateApi, BingoBoardDeleteApi, ...)
└── payload/                # request/ and response/ DTOs (controllers map domain → response factories)
```

Global infra-free code (`global/response/`, `global/filter/`, `global/handler/`, `global/config/`) lives in boot-web.
JPA base types (`BaseEntity`, `BaseAggregateRoot`, `BaseCreatedTimeEntity`) live in `gb-db-core/global/domain/jpa/`.
FileInfo domain is in `gb-domain-core/global/domain/file/`; FileInfoEntity + adapter in `gb-db-core/global/domain/file/`. Pure-NIO `FileStorage` (delete + path) lives next to `FileInfo` in domain-core; web-only `FileProvider` (upload via `MultipartFile`, find via `Resource`) stays in boot-web.

## Hexagonal Conventions (established over Phase 5a–6h refactor)

### Pure domain (gb-domain-core)
- `private constructor(...)` + `create(...)` / `of(...)` factory methods. `create` is for new aggregates (id=0L), `of` for rehydration from entity.
- Domain objects are **mutable** for aggregates with deep mutation paths (bingo, member). Mutators are domain methods (`board.completeBingoItem(itemId, memberId)`), not raw setters. Use `private set` for vars.
- Single-instance helpers like `withX()` (member) return `copy(...)` for immutable patterns — use data class when appropriate (member, friend).
- Domain events: aggregate root collects via `private fun registerEvent(event)` → `fun pullEvents(): List<Any>`. Adapter drains and forwards to JPA entity (see below).
- VOs (`BingoSize`, `BingoGoal`, `BingoPeriod`, `FileInfo`) are pure Kotlin with `init { ... }` invariants or factory validation.

### Ports (gb-domain-core)
- Location: `...<ctx>.domain.port.<Xxx>CommandRepository` + `<Xxx>QueryRepository`.
- Command vs Query split (`MemberCommand/QueryRepository`, `FriendCommand/QueryRepository`, `BingoBoardCommand/QueryRepository`, `BlockedMemberRepository` for simple cases).
- Single-result queries return **non-null** — adapter throws `XxxInputException` when not found. `OrNull` suffix if nullable is genuinely desired.
- Parameter/return types are domain objects. **No entities leak through ports.**
- Method naming per `code-implementation-rules` rule 13: `findOne` (single) vs `find` (plural). Parameter name vs method suffix: `findOne(id)` over `findOneById(id)` unless overload disambiguation is needed.

### Entities + Adapters (gb-db-core)
- Rename is consistent: `XxxEntity` for @Entity, `XxxEmbeddable` for @Embeddable, `XxxJpaRepository` for Spring Data interface, `XxxRepositoryAdapter` for `@Repository` port implementation.
- Entities have three standard methods:
  - `toDomain(): Xxx` — constructs pure domain, eagerly loads needed fields (e.g. profileUrl via nested toDomain call).
  - `companion object.from(domain: Xxx): XxxEntity` — entity from domain (for create path).
  - `applyChanges(domain: Xxx)` — mutates entity fields from domain (for update path).
- Adapter `save(domain)` = `JpaRepository.save(Entity.from(domain))` + `domain.pullEvents().forEach { entity.publishEvent(it) }`.
- Adapter `update(domain)` = fetch entity → `entity.applyChanges(domain)` → `syncChildren(entity.children, domain.children)` (id-matched add/update, orphanRemoval for deletions) → publish events.
- Aggregate events flow: domain collects → adapter drains via `pullEvents()` → entity's `publishEvent(event)` (`= andEvent(event)` from `BaseAggregateRoot`) → Spring Data's `@DomainEvents` + `@AfterDomainEventPublication` fires post-commit.
- `@OneToMany` / `@ManyToOne` are used **only inside a single aggregate boundary**. Cross-aggregate references are ID-based (`memberId: Long`, `bingoBoardId: Long`).
- Cascade ALL + `orphanRemoval = true` on aggregate root collections; sync logic relies on this.

### DAOs (gb-db-core)
- QueryDSL-only. Return `@QueryProjection` types (`BlockedMemberTargetInfo`, `FriendMemberInfo`, `FeedItemInfo`, `NotificationWithMemberProfile`) or `XxxEntity` lists for internal adapter consumption.
- **Never return `MemberEntity` or other foreign-aggregate entities to services or responses** — projections flatten the needed columns.
- Simple JpaRepository-sufficient lookups (`findById`, `findByEmail`) go through the adapter, not a DAO.

### Services (gb-domain-core/application)
- `@Service` orchestrator only (`code-implementation-rules` rule 1). No business logic, no `if/else` with database fetches.
- Inject only **ports** and **domain components** (`@Component` validators like `SignUpValidator`, `PasswordVerifier`). No direct `JpaRepository` or DAO in services — exceptions noted below.
- Allowed DAO injections: QueryDSL read DAOs returning projections (e.g. `FriendFindDao`, `BlockedMemberFindDao`, `FeedListFindDao`). These are infra but return projections, not entities. The DAO interface lives in domain-core; the QueryDSL implementation in gb-db-core.
- One Service + one Api per use case — `BingoBoardCreateApi/Service`, `BingoBoardDeleteApi/Service`, etc.
- Multi-repository validation (existence check, duplicate check, ownership) → extract `@Component` Validator (`SignUpValidator`, etc.).
- **Return domain types, not response DTOs.** Services return `Member`, `BingoBoard`, `BingoMap`, projections (`FriendMemberInfo`), or service-level domain DTOs (`AuthenticatedMember(member, accessToken)`, `BingoBoardDetail(bingoBoard, viewer, otherMembers)`). The controller maps to response DTO via factory.
- **File side-effects from domain-core**: pure NIO helper `FileStorage.delete(FileInfo)` lives in `gb-domain-core/global/domain/file/application/`. Web-only `FileProvider` (boot-web) keeps `upload(MultipartFile)`, `find(): Resource`, `getContentType` — controller uploads first, passes `FileInfo` into service so `MultipartFile` does not leak into domain-core.

### Responses (gb-boot-web/payload/response)
- Factory methods (`FriendResponse.of(info)`, `MemberResponse.of(authenticatedMember)`, `BingoBoardDetailResponse.of(detail)`, `BingoBoardResponse.fromBingoBoard(board, memberId)`) — no primary-ctor-in-controller.
- Accept domain or projection types, not entities. `@ResponseBody` serialization uses field names as-is.
- Wrapped in `ApiResponse.OK(data)` from the controller — do not return bare DTOs. Paged = `PageResponse`.

### Api / Controllers (gb-boot-web/api)
- Inject **services only**. No direct repository/DAO access (rule 12).
- Map service-returned domain object → response DTO via response factory before wrapping in `ApiResponse.OK`.
- `memberId: Long` via `@AuthenticationPrincipal` — `JwtProvider.getAuthentication` sets principal to the numeric ID.

## Security / Auth

- Stateless JWT via `JwtAuthenticationFilter` (before `UsernamePasswordAuthenticationFilter`).
- `SecurityConfig` uses Spring Security 6 lambda DSL (`.csrf { it.disable() }`, `.authorizeHttpRequests { ... }`, `.sessionManagement { ... }`).
- Auth-free endpoints hardcoded in `GET/POST/PATCH_AUTH_WHITELIST` arrays — **add new public endpoints here**, not via annotations.
- `JwtProvider` signs with a checked-in HS512 secret, 1-year expiry. Claims: `memberId` (Long) + `role` (`MemberRole` name).
- `PasswordEncryptor` port (`gb-crypto-core`) abstracts BCrypt. `TokenManager` port (`gb-jwt-core`) wraps `JwtProvider`.
- Auth context (`gb-domain-core/domain/auth/`) is separate from Member: `SignUp/Login/SocialLogin/PasswordReset/EmailFind` services live in `domain.auth.application`, return `AuthenticatedMember(member, accessToken)`. Member context keeps `NicknameEdit`, `NotiUpdate`, `ProfileEdit/Delete`, `Withdrawal`.
- CSRF is disabled (stateless API).

## Testing Stack

- **Kotest `BehaviorSpec`** (`Given/When/Then`) is the default. `test/.../config/KotestConfig.kt` sets `IsolationMode.InstancePerLeaf` and Spring test extensions. **MockK via `springmockk`** — Mockito is excluded from `spring-boot-starter-test`; do not re-introduce.
- **`@ApiTest`** (`test/.../config/ApiTest.kt`) is the controller slice meta-annotation: pulls `@WithAuthMember` (default memberId=1), imports `SecurityConfig`, enables `@AutoConfigureRestDocs`. Pair with `@WebMvcTest(controllers = [YourApi::class])` and `@MockkBean` for services.
- **REST Docs** — every controller test ends with `.andDocument("identifier", snippets...)` using the DSL in `test/.../docs/RestDocsExtensions.kt` (`requestBody`, `responseBody`, `responseBodyWithPage`, `pathVariables`, `requestParts`, etc.). `responseBody` auto-appends `code` + `message`. Snippets write to `build/generated-snippets`; `src/docs/asciidoc/api.adoc` combines them; HTML lands on the classpath under `/docs/**`.
- **Persistence tests** — `@LocalPersistenceTest` (H2, `@EnableJpaAuditing`, `@DataJpaTest`-based slice) or `@ProductPersistenceTest` (real MySQL, use sparingly). Both keep the real datasource (`Replace.NONE`).
- **Port-based tests**: `@LocalPersistenceTest` slice does **not** auto-load `@Service`/`@Component`/`@Repository` adapters. Add `@Import(XxxRepositoryAdapter::class)` when the test needs the port. Spring Data `JpaRepository` interfaces ARE auto-loaded.
- **JWT in tests** — `extension/JwtExpression.kt` exposes `getHttpHeaderJwt(memberId)` for supplying an `Authorization` header in MockMvc calls.

## Things Easy to Miss

- `open-in-view` is **disabled** — lazy collection access outside a transaction will throw.
- `data-local.sql` is loaded only under the `local` profile, **after** JPA creates the schema (`defer-datasource-initialization: true`).
- `p6spy-spring-boot-starter` reformats SQL in logs; `spring.jpa.show-sql` stays off in `local`.
- Firebase Admin is initialized from `src/main/resources/firebase/groubing-68b92-firebase-adminsdk-*.json` via `FcmConfig` in `gb-fcm-sender`. FCM failures surface as `FirebaseMessagingException`, mapped to `SERVER_ERROR` (HTTP 500) in `GlobalExceptionHandler`.
- BootJar archive is `api.jar` (no version suffix via `archiveVersion.set("")`) → `build/libs/api.jar`.
- **SQL soft delete**: `MemberEntity` uses `@SQLRestriction("active = true")` — inactive members are invisible at JPA query level. Account-withdrawn users won't appear in `findById`, joins, etc.
- **Adapter deep-sync**: `BingoBoardRepositoryAdapter.update(domain)` matches children by id. Adding a child with `id = 0L` inserts; existing ids update; entities absent from domain get orphan-removed. Children never lose their id across fetch/mutate/save.
- **Package paths preserve across modules** — e.g. `com.beside.groubing.groubingserver.domain.friend.domain.Friend` exists in gb-domain-core; `com.beside.groubing.groubingserver.domain.friend.entity.FriendEntity` in gb-db-core. This is intentional (meet-again pattern), not a split-package bug.
- **Service-returned domain DTOs**: `AuthenticatedMember(member, accessToken)` (auth flows), `BingoBoardDetail(bingoBoard, viewer, otherMembers)` (BingoBoardFindService) — these are pure data classes in domain-core, not response DTOs. Controllers map via `MemberResponse.of(authenticatedMember)` / `BingoBoardDetailResponse.of(detail)` factories.
- **MockK-mocking static companion in tests**: When a controller now calls a `FileProvider.Companion` method (e.g. `FileProvider.upload(multipart)`) that previously sat inside the service, stub it via `mockkObject(FileProvider.Companion)` in `beforeSpec` + `unmockkObject` in `afterSpec`. See `MemberProfileEditApiTest`.
