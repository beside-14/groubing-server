# 상세 구현 계획 작성 규칙 (Detail Plan Rules)

requirement-planner 에이전트가 `/detail-plan` 커맨드로 상세 구현 계획을 작성할 때 따르는 규칙.
추상적인 설명이 아닌, **개발자가 바로 구현할 수 있는 수준의 구체적 설계**를 제공한다.
단, **코드 스니펫은 포함하지 않는다.**

---

## 1. 문서 구조

```markdown
# Design: {기능명}

> 작성일: YYYY-MM-DD

## 1. 설계 개요
한두 문장으로 무엇을 어떻게 구현하는지 요약

## 2. 아키텍처
ASCII 다이어그램으로 레이어 간 호출 흐름 시각화

## 3. 상세 설계
파일별 변경 내용 (시그니처, 파라미터, 반환타입 수준)

## 4. 구현 순서
의존성을 고려한 순서 테이블

## 5. 고려사항
기술적 제약, 성능, 안전성 검토
```

---

## 2. 아키텍처 다이어그램 (필수)

레이어 간 의존 관계를 ASCII 박스 다이어그램으로 표현한다.

```
┌─────────────────────────────────────────────┐
│ boot/ma-boot-web (또는 ma-boot-batch)       │
│  Controller/JobConfig                       │
│    └── 호출 흐름 설명                        │
└──────────────────────┬──────────────────────┘
                       │ (port)
┌──────────────────────▼──────────────────────┐
│ domain/ma-domain-core                       │
│  Port Interface                             │
│    + 메서드시그니처(파라미터): 반환타입       │
└──────────────────────┬──────────────────────┘
                       │ (implements)
┌──────────────────────▼──────────────────────┐
│ infrastructure/storage/ma-db-core           │
│  Repository → DAO                           │
│    └── 쿼리/로직 설명                        │
└─────────────────────────────────────────────┘
```

---

## 3. 상세 설계 작성 규칙

### 파일별 섹션 구성

각 변경 파일마다 다음을 포함한다:

1. **파일 경로** (전체 모듈 경로)
2. **변경 유형** (신규 / 수정 / 삭제)
3. **메서드 시그니처** (파라미터명, 타입, 반환타입)
4. **변경 내용 설명** (무엇을 왜 변경하는지 한두 줄)
5. **기술적 포인트** (사용하는 API, 주의사항)

### 작성 형식

```markdown
### 3.X 레이어명 - 클래스명

**파일**: `모듈/src/main/.../ClassName.kt`
**변경 유형**: 수정

- `fun newMethod(param: Type): ReturnType` 추가
- 기존 `existingMethod()` 파라미터에 `newParam: Type` 추가
- **포인트**: Exposed DSL의 `deleteWhere`는 limit 미지원, 서브쿼리로 대체
```

### 절대 포함하지 않는 것

- 전체 클래스 코드
- import 목록
- 메서드 구현 본문
- 기존 코드 복사

---

## 4. 구현 순서 테이블 (필수)

| # | 파일 | 변경 유형 | 내용 |
|---|------|-----------|------|
| 1 | `domain/.../port/SomeRepository.kt` | 수정 | `fun delete(id: Long)` 메서드 추가 |
| 2 | `infrastructure/.../dao/SomeDao.kt` | 수정 | `deleteWhere` 구현 |
| 3 | `infrastructure/.../repository/SomeCoreRepository.kt` | 수정 | 포트 구현, DAO 위임 |
| 4 | `boot/.../SomeConfig.kt` | 신규 | Job/Controller 정의 |

- **변경 유형**: 수정 / 신규 / 삭제
- **의존성 순서**: port → dao → repository → boot

---

## 5. 고려사항

판단 근거와 대안을 간결하게:

```markdown
- **FK 안전성**: 참조하는 쪽이므로 삭제해도 FK 위반 없음
- **성능**: 인덱스 없으면 full table scan → 인덱스 추가 권장
- **대안**: 미지원 시 raw SQL로 대체
```

---

## 6. 프로젝트 컨텍스트

### 기존 패턴 참조 (필수)
변경 대상과 유사한 기존 구현체를 반드시 확인하고 일관성을 유지한다.

### DDL 변경 시
`infrastructure/storage/ma-db-core/src/main/resources/script/ddl.sql`에 추가. FK 사용 금지.

### 기존 코드 읽기 (필수)
구현 계획 작성 전에 변경 대상 파일의 현재 코드를 반드시 읽는다.

---

## 7. 파일 저장 규칙

**저장 경로**: `docs/requirement/{YYYYMM}/{feature-name}.requirement.md`

---

## 8. plan vs detail-plan 차이

| 항목 | `/plan` | `/detail-plan` |
|------|---------|----------------|
| 아키텍처 다이어그램 | 없음 | **있음** |
| 메서드 시그니처 | 간략 | **상세 (파라미터 설명 포함)** |
| 파일별 변경 설명 | 한 줄 | **여러 줄 + 기술적 포인트** |
| 고려사항 | 간략 | **대안/근거 포함** |
| 코드 스니펫 | 없음 | **없음** |
